# Generated application certification

## Candidate scope

This receipt records the `2.0.0-alpha.4` base candidate generated by
`knowme-builder` at commit
`626f0e598c7318f40505090cab4c5ddd8dd638f0`. A corrective follow-up makes the
second Android instrumentation run a strict read-after-restart check. That
follow-up remains pending exact-head native CI. A green compiler check alone
is not treated as application evidence.

The certified baseline contract is one persisted notes vertical slice through
clean architecture: UI, application/use-case boundary, repository port, Rust
implementation, and SQLite persistence. Optional auth, inference, UAR, module,
and legacy-embed integrations are separate capabilities and are not certified
by this receipt.

The iOS limitation is assigned to CI with exact Flutter `3.47.5`. The workflow
builds one debug simulator `.app`, then the portable Node helper derives its
bundle identifier with native `plutil` and drives that exact application binary
to create the note through the UI. It terminates the process with `simctl` and
relaunches the same installed binary through the restart-verification route.
The on-device test publishes a bounded sandbox marker only after the restarted
widget tree renders the note loaded through Rust FFI and SQLite. The local
partial result is retained instead of being promoted to a pass.

## Native release matrix

The workflow in `.github/workflows/scaffold-ci.yml` is the release authority
for host-specific evidence:

- Windows Server 2025 x64 with `x86_64-pc-windows-msvc`;
- Windows 11 ARM64 with `aarch64-pc-windows-msvc`;
- macOS ARM64 with Flutter 3.47.5, Android ARM64 debug-APK verification,
  an x86_64 emulator companion, and ARM64 iOS simulator execution;
- Ubuntu 24.04 with an API 35 x86_64 Android emulator that executes the
  instrumented companion built from the same generated project;
- Linux web runtime and compatible brownfield alteration.

Both Windows jobs launch the packaged native executable and use WebView2's
DevTools Protocol from the compiled TypeScript runtime to drive the rendered
React UI. A certification-only environment setting is passed through Tauri's
Rust-side `additional_browser_args` API; the web frontend cannot supply browser
arguments. The gate enters a note, invokes the Tauri command boundary,
terminates the entire first process tree, launches a second process with a fresh
browser profile against the same isolated application-data directory, and reads
the persisted note through the UI. SQLite-file creation alone is not accepted
as runtime proof.

The last complete base-candidate matrix is
[GitHub Actions run 36292024517](https://github.com/Know-Me-Tools/hybrid-mobile-architecture-skill/actions/runs/36292024517).
Every job passed at the candidate commit. The matrix built and executed the web,
brownfield, Windows x64, Windows ARM64, iOS, and Android targets. The Android
debug APK retained ARM64-only native code; a separately retargeted x86_64
debug companion from the same generated project supplied runnable emulator evidence.
The corrective strict-restart implementation must pass a new exact-head matrix
before this receipt can become final.

## Architectural and migration assertions

- Generated surfaces consume the same Rust domain and repository contracts.
- Flutter bridge and Riverpod outputs are generated before analysis/build, then
  receive and verify the `TJ-ARCH-MOB-001 compliant` marker through the portable
  Node helper.
- Alpha.3 outputs use a named, exact migration rather than a version-only no-op.
- Conflicting edited files produce proposal sidecars and do not advance the
  applied version.
- Capability additions use application-owned registry files and the same
  journaled preview/apply plan.
- Unsupported capability kinds fail before writing.
- Repeated successful generation, migration, and supported feature addition are
  idempotent.
