# Hybrid architecture portability and scaffold reliability

## Outcome and boundaries

Deliver a Windows-compatible skill package whose hooks and portable orchestration are authored in TypeScript 7 and shipped as Node.js `.mjs`. Prefer the existing native Rust `knowme-builder` for generation, filesystem ownership, native toolchain checks and platform work. Support Windows x64 (`x86_64-pc-windows-msvc`) and ARM64 (`aarch64-pc-windows-msvc`) explicitly. Do not equate installed Rust targets with working Windows linkers, native dependencies or runtime proof.

The user selected all first-party tooling and generated scripts as the conversion boundary; unavoidable vendor build internals are allowed and must be identified. Convert installers, hooks, validators, scaffold wrappers, CI helpers and first-party emitted platform scripts. Third-party vendored code and immutable historical evidence are not rewritten. Full and mini must consume the same portable payload; no full-pack checkout, Bash, Python or jq may be needed by a skill consumer.

Greenfield creation, brownfield adoption/alteration, and continued upgrades of previous outputs are equal product workflows. Existing applications keep their architecture and user-owned behavior while adoption reports the gap to the selected profile. Changes require an inspectable migration plan rather than a replacement scaffold. Treat earlier outputs as supported inputs with explicit version compatibility, not as disposable examples.

After tooling conversion, repair baseline profiles. Optional inference, auth, cloud and product integrations need separate capability checks and evidence; a baseline passing does not certify those integrations. Reject unsupported or invalid combinations before writing into the destination. Never silently ignore or coerce requested options.

## Ordered implementation

1. **Project tools and management.** Use the isolated `codex/hma-portable-tooling` checkout; preserve pre-existing source checkout changes. Extend existing OpenSpec with `init --tools all` and retain local metadata normalization. Build Compass structural graph plus Program IR over canonical sources, excluding mirrors/vendor/build artifacts; configure project-scoped stdio MCP without overwriting existing servers and verify initialization, tool listing and a bounded source query. Create inspectable project agent definitions using agent-team-creator, with disjoint ownership and an independent reviewer. Preserve KBD lifecycle authority rather than silently reconciling conflicting active-phase labels.
2. **Portable runtime foundation.** Pin `typescript=7.0.2`, use strict NodeNext `.mts` sources and emitted `.mjs`, with a committed lockfile and no compilation required at hook invocation. Match the existing package Node pin; separate development compiler requirements from consumer runtime requirements. Use Node builtins for JSON, paths, hashing, traversal and process orchestration. Avoid shell interpolation; resolve JavaScript CLIs to Node entrypoints and invoke native executables with argument arrays. Vendor-required batch entrypoints receive explicit, tested adapters rather than an assumed generic `shell:true` policy. Preserve exit codes, stdout protocol and stderr diagnostics.
3. **Hooks and installers.** Port activation/a11y hooks, hook installation/validation and harness installation/synchronization. Preserve advisory non-blocking behavior, malformed-input handling, manifest lookup, config merge semantics and user-owned files. Test Unicode/spaced paths, Windows separators, missing tools and hook JSON framing. Rebuild emitted files deterministically and update canonical templates/mirrors/manifests together. Remove superseded first-party shell/Python only after parity is demonstrated and all live callers are migrated.
4. **Native tooling and remaining scripts.** Extend existing Rust CLI rather than introduce a second generator. Add native environment/target diagnostics and explicit target-install commands; diagnose Windows MSVC/SDK and relevant native library support separately. Convert remaining first-party tools either to Rust native subcommands or `.mjs` orchestration according to responsibility, retaining observable behavior. Maintain an enumerated migration ledger; every executable and live reference must have a migrated destination or an evidenced vendor exemption. Port CI commands and generated Android/iOS orchestration, preserving host restrictions. Do not claim completion while old first-party runtime scripts remain.
5. **Runnable profile contract.** Unify legacy scaffold entrypoints behind typed Rust inputs. Make `--check` report requirements without destination writes. Generate into staging and promote only after required generation/structural validation; failed generation must preserve an existing destination. Separate generated, build-verified and runtime-verified statuses in evidence. Keep adoption/upgrades non-destructive and preserve owned-file digests. Add a single real clean-architecture feature through UI, state/use-case, repository port, Rust implementation and persistence, with restart persistence proof and surfaced errors.
6. **Brownfield and continual evolution.** Extend `adopt --check/--apply` to inventory real surfaces, dependencies and existing ownership; report incompatible layouts and incremental integration steps without claiming a missing surface exists. Adoption initially owns only newly added control files. Capability additions must integrate a functional vertical slice into the mapped project rather than merely create snippets under `.knowme-builder/additions`. Preserve original rendering inputs independently of destination directory names. Add versioned migration IDs, old/new version ranges, dry-run diffs and a persistent journal to `upgrade`; check the complete plan for conflicts before changing managed files. Preserve original bytes/backups and exact ownership metadata for rollback. Add/rename/remove template files through explicit migrations; never infer deletion of user files. Use prior generated content plus current content plus new template for conflict classification; write proposals for conflicts and do not advance the applied version on failure. Unsupported old versions receive a migration diagnostic, never a successful no-op. Schema/config/dependency/codegen migrations are tracked; destructive application-data migrations require a separately reviewed plan and backup. Verify upgrade idempotence, interruption recovery and rollback before claiming continuous upgrade support.
7. **Baseline profiles.** Provide complete React/Axum web, Tauri/React desktop, Flutter/Rust FFI mobile and sovereign hybrid applications with entrypoints, manifests, lockfiles, bridge/codegen configuration and documented run commands. Preserve Flutter+Rust for iOS/Android, React/Tauri for desktop, the shared Rust domain and repository rules. Complete Rust bridge codegen and Flutter generated provider/model code before analysis/build; build leaves together with their core. The governed web shell requires an explicit UAR prerequisite or a clearly reported unavailable service; do not replace its service contract with a fake success. Do not solve runnability by deleting architectural layers or optional capability claims without recording the limitation.
8. **Distribution and release evidence.** Add portable payload staging and integrity verification for full and mini, with the same bytes and all transitive package resources. Test installation from an isolated staged package, not a source checkout. Update current skill instructions, CLI examples, version references and migration documentation. Stage package integration changes separately from publication; release only after the matrix below passes.

## Verification matrix and acceptance

- Portable tools: macOS, Linux, Windows x64 and native Windows ARM64. Verify hook protocol, installer idempotence, user-config preservation, process exit handling, case-insensitive collisions, reserved names, traversal and spaced/Unicode paths. A unavailable runner is blocked evidence, not a pass.
- Native builder: clippy, public CLI behavior tests, existing adopt/upgrade ownership tests and target-aware preflight. Both Windows targets must compile with required MSVC/SDK dependencies on appropriate runners; host execution receipts are separate from cross-check receipts.
- Brownfield/upgrade: representative existing React/Axum, Tauri and Flutter projects with user edits, nonstandard directories and unrelated dependencies; previous Builder outputs with pristine and edited managed files; unsupported old schemas; additions/removals/renames; moved project directories; failure midway through apply and rollback. Dry runs leave byte-identical trees, conflicts never overwrite user work or advance the release marker, repeated successful migrations are no-ops, and each migrated baseline rebuilds and runs. Initial historical support is the checked-in Builder schema 1 and its `2.0.0-alpha.3` outputs plus fixtures from preceding releases where discoverable; unsupported histories remain explicit until fixtures prove a migration.
- Fresh generated web: locked dependencies, TypeScript check, production frontend/server builds; launch HTTP service/browser, invoke Rust feature, persist, restart and read back.
- Fresh generated desktop: React and Tauri build on each claimed host/architecture; launch native app, invoke Rust command, persist and restart. Reject target-specific dependency gaps instead of advertising unsupported Windows ARM64 combinations.
- Fresh generated mobile: bridge generation, Dart model/provider generation, analysis and native Android build/device or emulator run; iOS build and simulator run on macOS. No exclusion of the FFI crate from certification. Physical-device-only inference capabilities remain separately uncertified until exercised.
- Hybrid: all baseline surfaces consume matching Rust domain/types and bridge versions; shared feature contract passes on each surface. Host-ineligible builds are reported as such and dispatched to appropriate runners.
- Full/mini package smoke: run shipped `.mjs` from a clean copied payload without shell/Python/full-pack dependencies; compare payload hashes, check manifests and live invocation references.
- Independent adversarial-review of the assessment/plan precedes implementation; review completed changes and evidence again before certification. No self-assigned review pass, no invented live platform evidence.

## Ownership and rollout

Four durable roles: coordinator (specs, research, orchestration, integration/CI and docs), portable-runtime maintainer (TypeScript runtime, hooks and portable package installation), native-scaffold maintainer (Rust builder and generated application profiles), independent reviewer (findings only). Shared files are edited by one owner at a time. Models inherit the configured native harness by default; a separately identified model reviews the packet where available. Team exports are definitions, not proof of a running autonomous service.

Work in reviewable changes: tooling setup and evidence; hook/runtime conversion; native tooling and remaining script conversion; baseline scaffolds; distribution/verification. Keep a migration ledger and an unresolved-evidence list current. Do not publish packages, mutate unrelated projects or fabricate all-platform support.
